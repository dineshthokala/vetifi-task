4. Part A: Dose calculator
The user searches for a drug, selects a species, enters body weight, and sees the dose range in mg and the volume range in mL.
1. The app must work offline from first launch, with the base dataset included in the app.
2. Where the data for a drug or species is missing, inconsistent or unusable, the app must say so clearly and must not calculate. Deciding
what counts as unusable is part of the task.
3. Weight may be entered in kg or lb, with decimals, and sometimes with a comma as the decimal separator (for example 4,5). Impossible
values must be rejected.
4. The interface should be simple and professional. The final volume must be impossible to misread, and the mg dose and concentration
should appear alongside it.
5. Part B: Search
1. Add at least 50,000 generated drug entries to the base dataset.
2. Search must tolerate spelling mistakes; for example, melokin and benzaprl should find the correct drugs. Exact matches should rank first,
then prefix matches, then approximate matches.
3. Results from an earlier, slower query must never replace results from a later one.
4. Report the typical and worst time from keystroke to results on a real midrange Android phone, and explain how you measured it. Typing
should not cause dropped frames.
6. Part C: Constant rate infusion
Some drugs are given continuously by adding them to a fluid bag. The update file in Part D introduces one such drug, Dopraxine, with a dose
expressed in mcg/kg/min.
The user enters body weight, dose rate, fluid rate (mL/hr) and bag size (mL). The app shows how many mL of drug to add to the bag and how
long the bag will last. You will need to work out the formula yourself. Pay close attention to units.
7. Part D: Dataset server
Corrections to drug data must reach users without a new app release. Build a backend service that publishes and serves dataset versions.
PostgreSQL is preferred; SQLite is acceptable. Running docker compose up should be the only setup step.
The service should provide the following endpoints:
Endpoint Description
GET /v1/manifest?schema=2&current=v14 Returns the latest version the client can use, whether a delta from the client's current
version is available, and the payload size and SHA256 hash. Supports ETag, returning 304
when nothing has changed.
GET /v1/datasets/{version}?from={base} Returns a delta from the base version where possible, otherwise a full snapshot. Deltas
spanning several versions must be combined correctly.
POST /v1/admin/datasets Publishes a new version. Requires admin authentication. Validates every entry and returns
errors that identify the drug and field. Published versions cannot be modified.
POST /v1/admin/withdraw Withdraws a drug, with a reason, as a new version.
POST /v1/calc_logs Accepts calculation records uploaded by the app. A repeated upload must not create
duplicates.
GET /health Reports service and database status.
In addition:
1. Every manifest and payload must be signed (Ed25519 is recommended). The app holds only the public key and must reject anything that
fails verification. Someone who gains control of the server host or the network path must not be able to change a dose.
2. If two administrators publish from the same base version at the same time, exactly one should succeed and the other should receive 409
Conflict. Repeating a publish request with the same idempotency key should return the original result.
3. The server must reject the same invalid data that the app rejects. Explain how you prevent the two sets of rules from drifting apart.
4. When started with CHAOS=1, the server should randomly return a tampered payload, an incorrect checksum, a truncated response or a
server error. The app must handle all four without changing its data.
5. Include integration tests that run against a real database, covering at least the concurrent publish case and delta combination.

8. Part E: Updates in the app
1. When a connection is available, the app checks the manifest in the background, downloads any update, verifies the signature and hash,
and applies it.
2. Updates must be applied atomically. If the app is closed or killed at any point during an update, it must start next time with either the
complete old data or the complete new data. Please demonstrate this with a test or a written manual procedure.
3. The dataset version must be visible on every result screen. Withdrawn drugs must not be calculable, and the user should be told why.
4. Each calculation should be stored on the device with its inputs, dataset version and result, and uploaded to /v1/calc_logs when a
connection is available.
5. No network request may be made at the time of calculation. The app must continue to work offline indefinitely with the data it holds.
9. Part F: Written questions
Please answer the following in DECISIONS.md, in no more than 200 words each. Give a clear answer in each case. We will check that your
app and server behave as your answers describe.
1. Small doses. A 2.5 kg kitten needs 0.07 mL. A 40 kg dog needs 38.4 mL. What exactly does your app display in each case, and when
should it refuse to round?
2. Missing species data. A senior vet on the content team suggests: "If the cat dose is missing, show the dog dose with a warning. Vets
know what they are doing." Give the strongest argument for this view, then make your decision.
3. Bag volume. Adding a drug to a fluid bag increases the volume of the bag. Does this affect your infusion result? Show with numbers
when it matters and when it does not, and explain what your app does about it.
4. Users who never update. A vet has been offline for five months and still has v14, with the incorrect Benzaprol concentration. What, if
anything, can the app do for them?
5. Leaked signing key. Your private signing key is published online. What can an attacker do, what happens to installed apps, and how do
you recover? If your current design cannot recover without an app release, say so and describe what you would change.
6. Limits of your design. Describe one specific situation in which your storage, search, server or update design would be the wrong choice,
and what you would use instead.
10. Part G: Code review
The three functions below come from an earlier version of a hypothetical dose app. For each one, list the problems you find, rank them by the

Function 1 (Dart)
double volumeMl(double weight, String unit, double dosePerKg,
String concentration) {
final kg = unit == 'lb' ? weight / 2.2 : weight;
final mgPerMl = double.parse(concentration.split(' ')[0]);
final doseMg = kg * dosePerKg;
return double.parse((doseMg / mgPerMl).toStringAsFixed(1));
}
